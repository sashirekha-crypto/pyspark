Fix the Issue:
default auto-broadcast threshold (usually 10MB to 50MB) and your cluster has sufficient RAM, you can manually increase the threshold using the spark.sql.autoBroadcastJoinThreshold configuration.
Optimize Data Formats: If you are broadcasting a DataFrame, ensure it is flattened to reduce JVM memory overhead, or cache it first to properly gauge its in-memory size via the Spark UI.
Implement Bucketing: Consider bucketing your large tables so that you can join them efficiently without any network shuffling or memory

Spark Architecture:
==================
 	The Driver Program creates the SparkSession and requests the Cluster Manager for worker nodes (executors). The Cluster Manager then allocates the required worker nodes/executors
	Lineage is recorded as transformations are applied to the data.
	When an action is invoked, the Spark SQL engine calls the Catalyst Optimizer, which applies logical and physical optimizations and generates multiple physical plans. Based on the cost model, Spark selects the optimal plan for execution(This happens based on the lineage that is recorded.)
	Spark creates a DAG (Directed Acyclic Graph) from the physical plan and uses the DAG Scheduler to divide it into stages and tasks for execution across the cluster
	Task scheduler assigns the task to worker nodes

    Jobs are divided into multiple stages, and each stage is further divided into multiple tasks.
    Job: Created when an action (like .show(), .collect(), .write()) is triggered.
    Stage: A job is split into stages based on shuffle boundaries. Each stage is a set of tasks that can be executed without shuffling.
    Task: Each stage is divided into tasks, where one task operates on one partition of the data.
    Number of Tasks = Number of partitions
	====================================================================================
	Action
	  ↓
	Job                        				:1 Action = 1 Job
	  ↓
	Stages (based on wide transformations)  :No. of Stages = No. of Wide Transformations + 1
	  ↓
	Tasks (based on partitions)             :No. of Tasks = No. of Partitions
	
	An action creates a job.
	Stages are divided based on wide transformations (stages = wide + 1).
	Each stage has tasks equal to the number of partitions.
	====================================================================================
	
    Pyspark's Architecture consists of the following components:

		 Spark Driver:
			The Spark driver is responsible to run program and creates the SparkSession, which is entry point for creating RDDs,DaraFrames, and Datasets
		 SparkSession

		Executors: Also run on the local machine

		Where Driver Runs: On the machine that submits the job (e.g., your laptop or gateway node)
		Executors: Run on the cluster
	 3.Cluster Mode
		Where Driver Runs: On the cluster itself (inside a worker node)
		Executors: Run on other worker nodes
	
Catalyst Optimizer :
------------------
	 The Catalyst Optimizer is a core component of Spark engine that improves query performance through rule-based and cost-based optimizations.
	 It transforms SQL queries or DataFrame operations into highly efficient execution plans.
	 It happens in four stages: analysis, logical optimization, physical optimization, and code generation.

		Unresolved Logical Plan:
			Created by the spark SQL or DataFrame parser. Table/column names not yet validated.
		Analyzed Logical Plan
			Validates table and column names using the catalog (metastore). (semantic check)
		logical optimization (Rule-based optimization)
			Applies rules like constant folding, predicate pushdown, and projection pruning.
				Constant folding: Precomputes constant expressions (2 + 3 → 5)
				Predicate pushdown: Moves filters closer to the data source
				Projection pruning: Only selects required columns instead of loading all data
		Physical  optimization (cost-based optimization)
			Based on cost estimation, it selects the most efficient physical execution strategy.
			For instance, it might choose a broadcast join over a shuffle join if one table is small.
		Selected Physical Plan (best one chosen)
		Executed by Spark Engine

Transformation:
--------------
		Transformations are operations that create a new RDD from an existing RDD
		Narrow Transformations:
			  In a narrow transformation, the number of partitions before and after transaction remains the same, no shuffling is involved,
			  and there is no data exchange between nodes across the cluster
			  Ex:  map(), flatMap(),filter(),union()
     	Wide transformations:Joins,groupBy,orderBy
			 In wide transformations, the number of partitions may change, shuffling is involved, and data is exchanged between nodes
			 across the cluster
			 Ex: groupByKey(), reduceByKey(), Join(), distict()
Lazy evalution:
--------------
		Lazy evaluation means Spark does not execute transformations immediately when they are called on an RDD or DataFrame
        The actual computation only happens when an action is triggered (e.g., collect(), count(), show()).
	
		Instead, it builds a logical execution plan (DAG)

Delta Tables:
-------------
	   A Delta table is a data table stored in a special format that supports updates, deletes, and versioning, unlike regular Parquet or CSV files.
	   Delta Table is a Parquet-based table stored in a data lake
	
	   It is built on top of Parquet files and offers features like ACID transactions, schema enforcement and evolution,
	   data versioning,time travel,efficient updates and deletes , upserts and audit history.
	
	   ACID:
	   Atomicity   : All or nothing: Either the entire transaction succeeds, or nothing happens.
	   Consistency : The database must go from one valid state to another./Rules, constraints, and triggers are enforced.
	   Isolation   : Multiple transactions can run at the same time without interfering.The final result must be the same as if they ran one after the other.
	   Durability  : Once a transaction is committed, the change is permanent — even if the system crashes right after.
	
	   Z-ordering
	   Liquid Clusterting (First 32columns)
	   Vacuum(0)
	   MergeSchema
	   spark.conf.set("spark.databricks.delta.retentionDurationCheck.enabled", "false") --> Default Value is 7Days
	   optimize  :command is used to compact small files into larger files, which improves query performance
		 Schema enforcement Vs Schema evolution
			 Schema enforcement ensures that incoming data strictly follows the table schema, and any mismatch in structure or data types is rejected
			 Schema evolution allows adding new columns dynamically during data writes.
			 Schema Enforcement → Strict (rejects mismatch)
			 Schema Evolution → Flexible (allows new columns)

Spark Joins :
============
	Broadcast join:
		 <10MB
	Shuffle Hash Join (SHJ):
		 One of the tables is small enough to fit in memory of each executor.
		 Spark can build a hash table of the smaller table and stream through the larger one.
		 Typically used when:
			Join keys are not sorted.
			Not eligible for broadcast join.
			The smaller table doesn't need to be huge, but must fit in memory.
		 If small_table is small enough but not small enough for broadcast, SHJ is preferred.
	Sort Merge Join (SMJ):
		 Both tables are large and cannot fit into memory.
		 Join keys are sortable and Spark can sort both datasets by the join key, then merge them.
		 Ideal for equi-joins on large datasets.


	Partitioning → Creates folders
	Bucketing → Creates files (based on hash of bucket columns)
	Z-ordering → Rearranges data within files
	Deletion Vectors → Creates sidecar metadata files
						Tracks logically deleted rows without rewriting Parquet files
	
	Partition By → Use partitioning to reduce data scanning by splitting data into folders based on commonly filtered, low-cardinality columns like date.
	Bucketing → Use bucketing to improve large joins by distributing data into fixed hash buckets to reduce shuffle.
	Z-ORDER (Delta in Databricks) → Use Z-ORDER to group related column values together in files to improve filtering performance.
	Liquid CLUSTER BY → Use Liquid Clustering to dynamically organize Delta data for better query performance without fixed partitions.
	OPTIMIZE (Delta) → Use OPTIMIZE to compact small files and reorganize data to improve query performance.
	
	Partitioning:
		Partitioning divides data into folders based on column values to improve query filtering performance.
		Example: sales data stored as year=2023, year=2024.
	Bucketing:
		Bucketing distributes data into a fixed number of files using a hash function to improve join performance.
		Example: employee data split into 8 buckets by dept_id.
 
	spark.sql.shuffle.partitions: This property controls the number of output partitions for wide transformations (like groupBy, joins, aggregations).
	The spark.sql.files.maxPartitionBytes setting (default 128 MB)

Memory Management:
=================
    OOM:
		OOM stands for Out Of Memory. It happens when Spark cannot allocate enough memory for processing data.
		This can occur on the driver when using collect or on workers during heavy operations like joins or aggregations
	
	In Spark, execution and storage memory are allocated from a shared pool using UNIFIED MEMORY MANAGEMENT.
	Execution memory is used for processing tasks and can take memory from storage if needed, while storage memory is used for caching and can be evicted when execution requires more space.
	
	Memory management in Apache Spark is how memory is used for processing and storing data. If memory is not enough or not used properly,
	it can cause OOM errors, slow performance, or data spilling to disk.
    We can fix this by writing efficient code, using proper partitions, avoiding collect, handling data skew,
	and using AQE in Databricks, which improves performance at runtime.
 
	WRITING EFFICIENT CODE MEANS PROCESSING LESS DATA BY FILTERING EARLY, SELECTING ONLY NEEDED COLUMNS, AND USING EFFICIENT JOINS.
	
AQE: It was introduced in version 3.0 and enabled by default starting from version 3.2
----
	AQE (Adaptive Query Execution) is a feature in Spark that optimizes queries at runtime using actual data statistics.
	It improves performance by
	1.Coalescing shuffle partitions --> Removes unnecessary shuffle partitions
	2.Dynamically switching join strategies -->Converting a Sort Merge Join to a Broadcast Join
	3.Handling skewed data      -->Merges small partitions and splits larger partitions

DLT (Delta Live Tables)
========================

	Delta Live Tables is a declarative framework in Databricks for building reliable ETL pipelines.
	Instead of managing orchestration manually, you just define tables and transformations, and DLT automatically handles dependencies,
	data quality checks, and lineage.
	It supports both batch and streaming data, which makes pipelines simpler, reliable, and easier to maintain

	1.Normal Databricks Notebooks
		You write imperative code (step by step).
		You are responsible for orchestration (order of execution).
		Must manually handle dependencies between tables.
		Monitoring, retries, error handling → need custom code or workflows.
		Data quality checks → must be written and maintained by you.
		Good for ad-hoc analysis and small ETL jobs.

	2. Delta Live Tables (DLT)
		Uses a declarative approach → you just define the tables and transformations.
		Dependencies are managed automatically (DLT knows which table depends on which).
		Built-in data quality checks using EXPECT clauses.
		Provides automatic lineage, monitoring, logging, and retries.
		Supports both batch and streaming pipelines.
		Good for production-grade, reliable ETL pipelines.
		Reliable → Pipelines are fault-tolerant, recoverable, and consistent

	1.Automatic Lineage
		If you define a sales_summary table built from orders and customers, DLT shows the lineage graph automatically, so you know exactly which source data feeds the summary.
	2.Monitoring
		If your daily pipeline that processes 10 GB of logs suddenly starts receiving 50 GB, DLT alerts you to the increased load.
	3.Logging
		If a data quality rule fails (e.g., order_id cannot be null), the logs capture how many records failed validation and why, making debugging easier.
    4.Retries
		If a temporary network issue prevents loading data into a target table, DLT retries automatically instead of requiring manual rerun.

ADF is mainly used for data movement, integration, and orchestration. It’s great for lift-and-shift scenarios, like copying data from on-prem systems to the cloud using built-in connectors.

>CTE vs subquery
Common Table Expressions (CTEs) and subqueries are both temporary result sets used to break down complex SQL logic, but they differ significantly in syntax, readability, and structural features. While a subquery is nested inline within a clause (like FROM or WHERE), a CTE is defined upfront using the WITH keyword, making it named, reusable, and dramatically easier to read A subquery is written inside another query and is harder to read and cannot be reused easily.

Yesterday the job was running fine, but today it’s slower — I approach this systematically.

So if data is different, I focus on volume and skew.
If data is same, I analyze Spark UI, execution plan, cluster behavior, and data layout to identify the bottleneck.

Data is NOT Same (Volume increased / Distribution changed)

	If data volume increased → more processing time is expected
	If data skew is present → some tasks run longer than others

	I use Spark UI to:
		Identify long-running stages
		Check for skewed tasks (uneven task duration / high shuffle read)
	Based on that, I optimize by:
		Repartitioning data properly
		Using salting techniques for skew (for highly skewed keys)
		Applying broadcast joins where applicable (to reduce shuffle)
	Additionally:
		I ensure efficient code by pushing filters early to reduce data before joins/aggregations
	For Delta tables:
		I run OPTIMIZE to reduce small files
		Use Z-ORDER to improve data skipping
	If Liquid Clustering is enabled:
		It can replace Z-ORDER for data skipping
		However, OPTIMIZE may still be required to manage file sizes
	AQE:
		AQE helps reduce skew impact at runtime
		But in cases of high or extreme skew, we may still need techniques like salting or repartitioning
	
Data is Same
	If both data and logic are same, then I focus on execution and environment changes.

	Spark UI Analysis
		Compare stages with previous run.Check (Shuffle increase/GC time/Task skew)
	
		GC time = time spent by Spark executors cleaning unused memory
		It is the time JVM spends removing unused objects from memory to free up space.
	
	Cluster / Environment Changes
		Cluster size (workers reduced?)/Autoscaling delays/Max worker limits/Cloud provisioning latency(delay in getting new machines (VMs) from the cloud provider)
	Execution Plan Changes
		Use explain() to compare plans
		Check if 1.Broadcast join → Shuffle join 2.Join strategy changed
	Data Layout Issues
		Even with same data, layout can change:
		Too many small files/Missing partition pruning/Table not optimized
			Fix:
				Run OPTIMIZE
				Adjust partitioning
	Caching Issues
		Cached data might be cleared
		Leads to recomputation

	External/System Factors
		Storage latency (ADLS / S3)

Data is ingested from multiple sources using ADF into ADLS.
Databricks processes the data using a medallion architecture — 
Bronze for raw data, Silver for cleansing and transformations,
and Gold for business-ready data. 
principal :
1. Layered Data Progression:
You don’t transform everything at once — you progressively refine data step by step.
2. Progressive Data Quality Improvement
Instead of fixing data in one go, quality checks and transformations are applied incrementally.
3. Separation of Concerns
Each layer has a clear responsibility:
Bronze → ingestion & historical storage
Silver → transformation & standardization
Gold → analytics & reporting
4. Single Source of Truth with Reprocessability
Raw data is always preserved in Bronze layer.
Data can be reprocessed anytime if business logic changes

Finally, the data is used for reporting through tools like Power BI.
The entire pipeline is metadata-driven with monitoring and logging

1.Can you explain how Auto Loader works in Databricks?
Auto loader incrementally processes new data files as they arrive in cloud storage.
It uses identifier called cloudFiles to point to an input directory path, automatically processing files without requiring any manual file tracking or scheduling setups.
it does exactly once processing ,its logs meta data within your pipeline by check point location,
If failure occurs auto loader resumes where it left off with out redundant processing.
Automatic Schema Inference & Evolution You do not need to provide a hardcoded schema. Auto Loader detects changes dynamically:

2.What are the schema evolution modes available in Auto Loader? Can you explain each mode with examples?
The four schema evolution modes are:
1.addNewColumns (default): Automatically adds new columns to your table schema as they are discovered. and ingests it on the next run.
Suppose your first few files contained id and name
New File: Contains a new age column.
Result: The stream fails, automatically adds age to the table schema, and ingests it on the next run
2.rescue : Any unexpected columns or data type mismatches are captured and bundled together in a special JSON blob column (usually named _rescued_data)
Your table schema has id and name.
New File: Arrives with an unexpected phone_number column.
Result: The stream processes the file smoothly without failing.
The phone_number data is not lost; it is placed neatly inside the _rescued_data column (e.g., {"phone_number": "123-456-7890"}).
3.failOnNewColumns :Auto Loader encounters any columns that were not in the initially inferred schema, the stream fails completely and will not restart until you manually update the schema
Your table schema has id and name.
New File: Arrives with a new column named address.
Result: The pipeline fails. It pauses data ingestion until you manually approve the new address column to alter the table structure.
4.none:Useful if you only need a specific set of base fields and intentionally want to discard newly introduced or temporary upstream fields.
Your table schema has id and name.
New File: Arrives with id, name, and an unexpected department column.
Result: Auto Loader ingests id and name as usual but entirely drops and ignores the department data.

Auto Loader ingests data into a Delta table. If a record is deleted in the source system, how would you reflect that deletion in Databricks?
Auto Loader only appends new or modified files; it cannot natively detect if a record was deleted in the source system. To propagate source deletions to a Delta table, you must capture the change events (CDC) from your source system and apply them using a MERGE INTO statement or Delta Live Tables (DLT). The Autoloader is designed to process files exactly once unless the option "cloudFiles.allowOverwrites" is enabled.

What is the use of Change Data Feed (CDF) in Databricks?
Incremental ETL: Process only the rows that have changed since the last pipeline run instead of reloading or comparing entire datasets.
